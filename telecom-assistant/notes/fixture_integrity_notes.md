## 1. The defect

> **Historical as of 2026-08-24 (marked 2026-08-25).** This section describes
> the **pre-repair** fixture. It was superseded by the gold1 re-fixturing on
> 2026-08-24, which re-authored gold1 as the concrete derivation
> "Time-shift property for a causal exponential" now in
> `src/error_injection.py`. The defect analysis below is kept as the record of
> what was wrong and why; it is no longer a description of the live fixture.
> Current state: §5a, and root `CLAUDE.md`, "Injection rows revised 2026-08-24".

`GOLD_FIXTURES[1]`, concept "Time-shift property", as written in
`src/error_injection.py`:

```
s1 [definition  ] integrate(x*exp(-I*omega*(t - t0)), (t, -oo, oo))
s2 [algebra     ] exp(-I*omega*t0)*integrate(x*exp(-I*omega*t), (t, -oo, oo))
s3 [substitution] exp(-I*omega*t0)*X
```

Two things are wrong with s1, and they compound.

**The shift is on the kernel, not the signal.** The time-shift property is
about the transform of a shifted signal, `x(t - t0)`. What s1 writes is the
signal multiplied by a *shifted exponential kernel*,
`exp(-I*omega*(t - t0))`.

**`x` has no dependence on `t`.** It parses as a bare `Symbol`, not an applied
function, so it carries no time argument that could be shifted, and it factors
straight out of the integral.

Expanding the integrand shows what the written expression actually means:

```
>>> sp.sympify("x*exp(-I*omega*(t - t0))")
x*exp(-I*omega*(t - t0))
>>> sp.expand(sp.powsimp(_, force=True))
x*exp(-I*omega*t)*exp(I*omega*t0)
>>> _ / (x*exp(-I*omega*t))
exp(I*omega*t0)
>>> type(sp.sympify("x"))
<class 'sympy.core.symbol.Symbol'>
```

So the constant that s1 pulls out of the integral is `exp(+I*omega*t0)`:

```
s1 = exp(+I*omega*t0) * Integral(x*exp(-I*omega*t), (t, -oo, oo))
s2 = exp(-I*omega*t0) * Integral(x*exp(-I*omega*t), (t, -oo, oo))    <- as written

>>> sp.simplify(sp.exp(sp.I*om*t0) / sp.exp(-sp.I*om*t0))
exp(2*I*omega*t0)
```

The sign of the phase factor is inverted between s1 and s2. s2 and s3 are
internally consistent with each other and state the property correctly; only s1
is wrong, which is why the defect survives casual reading of the derivation.

**Both judges flagged this correctly.** Their objection to the step is not a
judge error to be counted against them. See §5 for what that means for the
tables, and `confidence_equivalents_notes.md` §8 for the dispute as it was
originally recorded.

A correct s1 would apply the shift to the signal and keep it a function of the
integration variable:

```
integrate(x(t - t0)*exp(-I*omega*t), (t, -oo, oo))    with x = Function('x')
```

under which the substitution `u = t - t0` yields `exp(-I*omega*t0)*X(omega)`,
which is what s2 and s3 already assert.

All 9 fixtures were audited on three checks.

**(c) Adjacent-step equivalence.** For each adjacent pair, `simplify(s_n -
s_{n+1})` under declared assumptions, with a random-point numeric probe as
tiebreak where `simplify` returns a guarded `Piecewise`. See §3 — the naive

**(a) Signal-domain operation written on the wrong object** — shift, scaling,

**There are zero `AppliedUndef` atoms anywhere in the corpus.** That is not by

limits `(t, 0, oo)` rather than through a step function, and every remaining
fixture operates on an explicit closed-form expression.

**gold1 is the only property-style derivation in the corpus.** Every other
fixture is either a concrete transform of a specific signal (gold0, gold5) or a
pure algebra/calculus identity on an explicit expression (gold2, gold3, gold4,
gold6, gold7, gold8). gold8's "Derivative of polynomial" is `diff(x**3, x)`,

differentiation property.

Two consequences follow, and the second is the uncomfortable one:

- The defect class has exactly one member, so nothing else in the suite needs
  the same repair.
- **There is no sibling fixture to validate gold1 against.** The one abstract
  property in the corpus was written once and never cross-checked against a
  second instance of its own kind. A corpus with two or three property-style
  derivations would have made the inconsistency visible by comparison.

## 3. False-alarm caveat: the naive equivalence test does not work

A regression test written as `simplify(s_n - s_{n+1}) == 0` **flags gold0,
gold5 and gold7 as broken**. All three are correct. SymPy returns a
convergence-guarded `Piecewise` rather than a bare `0`, because it will not
assert an equality that holds only on part of the parameter domain.

`gold7` is the compact example:

```
>>> sp.simplify(Sum(r**n, (n, 0, oo)) - 1/(1 - r))
Piecewise((1/(1 - r), Abs(r) < 1), (Sum(r**n, (n, 0, oo)), True)) + 1/(r - 1)
```

Not `0`, and not obviously zero. Calling `.doit()` on the sum first, then
simplifying, resolves it:

```
>>> Sum(r**n, (n, 0, oo)).doit()
Piecewise((1/(1 - r), Abs(r) < 1), (Sum(r**n, (n, 0, oo)), True))
>>> sp.simplify(_ - 1/(1 - r))
Piecewise((0, (r > -1) & (r < 1)), (Sum(r**n, (n, 0, oo)) + 1/(r - 1), True))
```

The first branch is `0` on exactly the domain where the identity is valid. That
is a pass, not a failure.

`gold0` and `gold5` fail the naive test the same way, guarded on the
convergence of their `(t, 0, oo)` integrals rather than on `|r| < 1`.

**Exact assumptions any such test must declare:**

```python
omega = sp.Symbol('omega', real=True)
t0    = sp.Symbol('t0',    real=True)
t     = sp.Symbol('t',     real=True)
a     = sp.Symbol('a',     positive=True)
s     = sp.Symbol('s',     positive=True)
r     = sp.Symbol('r',     real=True)      # probed only on |r| < 1
n     = sp.Symbol('n',     integer=True, nonnegative=True)
```

plus `.doit()` on infinite `Sum` (and `Integral`) nodes before comparison.

Without the assumptions, a numeric probe is also unreliable: sampling `omega`
off the real line puts the transform integrals outside their region of
convergence, and `sp.N` on an undoit'ed infinite `Sum` silently truncates. Both
produced spurious "NOT EQUAL" verdicts during this audit before the assumptions
were declared. **A fixture-integrity test that is not domain-aware will cry
wolf on a third of the corpus and be switched off.**

## 4. The sanity-gate hole

The suite has a baseline gate, `filter_viable_fixtures`, at
`src/error_injection.py:675`. Its stated job is to drop any fixture the
verifier objects to before mutation, so a flag on a mutated trial can be
attributed to the mutation rather than to a bad fixture.

The guard, `src/error_injection.py:690`:

```python
bad_steps = [r.step_number for r in results if r.is_valid is False]
```

and the branch it feeds, `src/error_injection.py:694-700`:

```python
if bad_steps:
    warnings.append(
        f"Fixture {i} ({g.get('concept','?')}) flagged at baseline: "
        f"steps {bad_steps} — dropping from suite"
    )
else:
    viable.append(g)
```

The test is `is_valid is False`. **Abstain is `is_valid is None`, which is not
`False`, so an abstaining baseline falls through to `viable.append(g)`.**

gold1's baseline abstains on both graded step indices:

```
verify_derivation(GOLD_FIXTURES[1], strict_mode=True)
  step_index 0 (s1): is_valid=True   equivalence_checked=False  message='First step'
  step_index 1 (s2): is_valid=None   equivalence_checked=True   message='Could not verify — review manually'
  step_index 2 (s3): is_valid=None   equivalence_checked=True   message='Could not verify — review manually'
```

`bad_steps` is empty, so gold1 entered the suite. It did so **silently** — the
`warnings` array is `[]` in both frozen reports, so no trace of the near-miss
exists in the artifacts.

Stated plainly: **the gate inherits the verifier's blind spot.** It asks the
verifier whether the fixture is wrong, and treats "I cannot tell" as "it is
fine." It cannot catch a defective fixture whose steps the verifier is unable
to decide, which is precisely the class of fixture most likely to be wrong,
since an unevaluable step is one nobody's tooling has ever checked.

And the specific miss is not incidental. `equivalence_checked` is `True` at
step_index 1, so **the verifier did attempt exactly the s1->s2 comparison that
would have exposed the sign inconsistency**, and abstained because the
`(-oo, oo)` integral is divergent as written. The one comparison that mattered
is the one that returned no answer, and the gate read that non-answer as
approval.

### 6a. Adjacent-step equivalence over every fixture

For each fixture and each adjacent pair, assert equivalence under the declared
assumptions of §3:

- parse both steps with the assumption locals, not bare `sympify`
- `.doit()` any `Sum` or `Integral` before comparison
- pass if `simplify(s_n - s_{n+1})` is `0`, **or** is a `Piecewise` whose branch
  conditions are satisfied on the fixture's declared parameter domain
- fall back to a random-point numeric probe drawn from inside that domain
- fail loudly, naming the fixture, the pair, and the residual

Against the current corpus this must report exactly one failure, `gold1`
`s1->s2`, and must not report gold0, gold5 or gold7. **Pin that expectation in
the test**, so that a future change to the assumption handling that silently
starts passing gold1 is caught by the count.

#### Limitation: a simplify-based check cannot certify an abstract property

The check specified above is built on `simplify`, and `simplify` is not
sufficient for a **property-style** fixture — one that asserts a transform
identity for an arbitrary signal rather than computing it for a specific one.

Concretely, for a correctly written abstract time-shift step with a genuine
`AppliedUndef` signal:

```
S0 = Integral(x(t - t0)*exp(-I*omega*t), (t, -oo, oo))
S1 = exp(-I*omega*t0)*Integral(x(t)*exp(-I*omega*t), (t, -oo, oo))

simplify(S0 - S1) == 0   ->  False
expand(S0 - S1)   == 0   ->  False
(S0 - S1).doit()  == 0   ->  False
```

SymPy has no shift theorem for an unevaluated integral of an undefined
function, so none of the §3 machinery closes it. The identity is provable, but
only through an explicit change of variables plus a bound-variable rename:

```
>>> S0.transform(t - t0, u)
Integral(x(u)*exp(-I*omega*(t0 + u)), (u, -oo, oo))
>>> # rename the dummy u -> t, then
>>> simplify(_ - S1)
0
```

Note the second half of that: even after `transform`, the residual is not `0`
until the bound variable is renamed, because `simplify` does not canonicalise
the dummy of an unevaluated `Integral` over an `AppliedUndef`.

Two consequences:

- **The check as specified would have reported gold1 `s1->s2` as a failure
  whether the fixture was defective or not.** Against the defective fixture it
  returns the right answer for the wrong reason. That weakens it as evidence:
  a passing corpus tells you the fixtures are concrete, not that they are
  correct.
- **Certifying a property-style fixture requires a transform-aware path** — a
  declared change of variables per fixture, plus dummy-variable canonicalisation
  before comparison. That is a materially bigger test than 6a describes, and it
  is not written.

This limitation is why the gold1 repair re-authored the fixture as a *concrete*
derivation (causality through integration limits, in the gold0/gold5 idiom)
rather than fixing the abstract form in place. The concrete form is certifiable
by 6a as specified; the abstract form is not. The corpus-level cost is recorded
in §2: after the repair the corpus contains **no** property-style derivation at
all, so the class of defect described in §1 can no longer occur in it, and
equally can no longer be detected by it.

### 6b. The gate must surface a baseline abstain — warn, do not drop

> **APPLIED 2026-08-26.** Implemented in `src/error_injection.py`
> (`filter_viable_fixtures`, `run_suite`, `Trial`, `_trial_to_dict`, `main`),
> with four regression tests in `scripts/test_error_injection.py` running under
> `scripts/run_tests.sh` (36/36 pass; was 32). The WARN-not-DROP decision below
> was implemented as written, and the reasoning for it is unchanged. What
> follows is a record of three refinements found during implementation. None of
> them changes the decision; the second is a genuine gap in the spec below.
>
> **R1. The gate discriminates three baseline outcomes, not two.**
>
> | verifier said | means | action |
> |---|---|---|
> | `is_valid is False` | refutes the step | **drop** (unchanged) |
> | `is_valid is None` + `equivalence_checked is True` | attempted the comparison, returned no answer | **warn, keep, flag every trial** |
> | `is_valid is None` + `equivalence_checked is False` | nothing was ever compared | **silent** |
>
> **R2. The silent case has two causes, and the spec below names only one.**
> "Test assertions" describes it as "a genuine first step". In this corpus it
> also covers **a step whose expression fails to parse**: that yields
> `is_valid is None` with `equivalence_checked is False` too. `Q09.1` on the
> human set is the live instance — it parse-fails, and `Q09.2` then takes the
> first-step branch behind it (`cascade_variants_notes.md` F7).
>
> Both must stay silent, and for the same reason. `equivalence_checked is False`
> means the verifier never performed a comparison, so its non-answer is a fact
> about the verifier's reach, not evidence about the fixture. Warning on it
> would be **§4's error in mirror image**: §4 records the gate reading an
> unperformed comparison as approval; warning here would read the same
> unperformed comparison as suspicion. Neither is licensed, because in both
> cases nothing was measured. Only the middle row — a comparison that was
> attempted and came back undecided — carries information, and it is the only
> row that warns.
>
> The practical cost of getting R2 wrong is also concrete: parse failures are
> common enough that warning on them would fill the `warnings` array with
> fixtures the gate has nothing to say about, and a noisy channel is one nobody
> reads, which is the failure mode §4 is about.
>
> **R3. Two identifiers, and a conditional field.** The warning carries both
> `gold_id` (index into `viable`, i.e. the id the fixture's trials actually
> carry, so the warning is joinable against `trials`) and `input_index`
> (position in the input list). They diverge as soon as anything ahead of the
> fixture is dropped; the spec's example below shows only one number.
> `step_indices` are **positional**, matching `Trial.step_index`, not the
> 1-based `r.step_number` the drop warning uses — the two conventions now
> coexist in one function. `baseline_undecidable` is serialized **only when
> true**; absent means false. That keeps unaffected trials byte-identical to the
> frozen reports, which the regrade/splice workflow in
> `confidence_equivalents_notes.md` §8a diffs against.
>
> Three of the four assertions below became automated tests. The fourth, the
> corpus-level one, costs 14.5s and is run by hand instead: see §7.

**Position: WARN. Do not drop the fixture.**

The gate's current contract is "not disproven"; it should become "the
undecidable case is recorded and propagated". It should *not* become "drop
anything unverified".

#### Why not drop

The verifier abstains on **76 of 118 graded injection trials, 64.4%**
(`error_injection_report_with_judge.json`; matches Table 1's symbolic injection
abstain rate of 0.644). Abstention is this verifier's normal operating mode on
this testbed, not an anomaly. The study's own finding is that a large fraction
of ordinary derivation steps sit outside the symbolic fragment.

A drop rule would therefore discard fixtures **for being outside the symbolic
fragment**, which is the result, not a fixture defect. It would let the
verifier's coverage decide the composition of the corpus used to measure that
same verifier's coverage, and it would bias the suite toward exactly the steps
symbolic tooling already handles.

That is **the blind spot inherited in the other direction**. §4 records the gate
trusting the verifier's "I cannot tell" as approval. Dropping would have the
gate trust the same non-answer as condemnation. Both readings treat an
undecidable result as though it carried information about the fixture. It does
not; it carries information about the verifier.

One scoping note, so the 64.4% is not over-read. That figure is trial-level and
covers mutated trials. At *baseline*, on unmutated steps, **gold1 is currently
the only fixture with an undecidable step**:

```
fixtures with >=1 abstaining baseline step (is_valid None, equivalence_checked True):
  gold1  Time-shift property    undecidable step_index [1, 2]
```

So a drop rule applied today removes exactly one fixture and 18 graded trials.
The argument above is about the rule being written, not about a large current
casualty list: the 64.4% establishes that undecidability is routine for this
verifier, which is what makes a drop rule the wrong standing policy even though
its immediate blast radius is small.

#### Rejected alternative, recorded

**Drop the fixture, as `filter_viable_fixtures` already does for
`is_valid is False`.** Rejected. It is the more consistent-looking option, since
it treats both non-pass outcomes alike, and it has the appeal of guaranteeing
every surviving fixture is affirmatively verified. Cost: it changes every
injection cell in Table 1 by removing 18 graded trials, it makes corpus
membership a function of verifier coverage, and on the argument above it draws a
conclusion about the fixture from a fact about the verifier. The consistency is
superficial — `False` is a verdict, `None` is the absence of one, and they
should not be handled alike.

#### The fix, concretely

On detecting a baseline abstain — `is_valid is None` at a step with
`equivalence_checked is True`, an attempted comparison that returned no answer:

1. **Append a structured entry to the report's `warnings` array.** That array is
   `[]` in both frozen reports today, so this condition currently leaves no
   trace anywhere in the artifacts. Structured, not a bare string, so it can be
   queried:

   ```json
   {
     "kind": "baseline_undecidable",
     "gold_id": 1,
     "concept": "Time-shift property",
     "step_indices": [1, 2],
     "detail": "verifier attempted equivalence and returned no verdict"
   }
   ```

2. **Set `baseline_undecidable: true` on every trial derived from that
   fixture.** Downstream analysis can then filter or stratify on it, and no
   consumer has to re-derive the condition by re-running the verifier — which is
   what §5 had to do, because `equivalence_checked` is not persisted.

3. **Keep the fixture in the suite.** No change to any published cell.

The two together mean the condition cannot be missed by someone who is not
reading stdout: it is in the report envelope and on each affected trial record.
That is the actual failure in §4 — not that the gate reached the wrong verdict,
but that it reached a silent one.

#### Test assertions

- `filter_viable_fixtures` emits a `baseline_undecidable` warning for a fixture
  whose unmutated steps include an `is_valid is None` at a step with
  `equivalence_checked is True`, and **retains** the fixture
- the case is distinguished from `equivalence_checked is False` — a genuine
  first step, which has nothing to compare and is not evidence of anything, and
  must produce no warning
- the warning reaches the report's `warnings` array, and `baseline_undecidable`
  is set on every trial from that fixture
- against the current corpus this fires for `gold1` and for no other fixture,
  and the graded trial count stays at 118

Both checks belong in `scripts/test_error_injection.py` alongside the existing
crash-as-abstain regression test, and should run under `scripts/run_tests.sh`.

## 7. Corpus-level scan of the applied gate, 2026-08-26

The fourth assertion in §6b's "Test assertions" — that against the current
corpus the gate fires for `gold1` and no other fixture, and that the graded
trial count stays at 118 — is **not** in `scripts/run_tests.sh`. It needs a
baseline `verify_derivation` over all 9 fixtures under `strict_mode`, which
takes **14.5s**. The suite is deliberately cheap: `test_main_writes_report`
already monkey-patches `GOLD_FIXTURES` down to two fixtures for the same

### The command

It lives here, in this note. It is not a script in `scripts/`, because a
14.5s check that is not wired into `run_tests.sh` would rot unnoticed as a file
nobody runs; recording it next to its result at least keeps the two together.
If it ever earns a home, the right one is a separate perf entry point, not
`run_tests.sh`.

```bash
cd telecom-assistant
PYTHONPATH=. ./.venv/bin/python3 - <<'PY'
import time
from src.error_injection import GOLD_FIXTURES, filter_viable_fixtures, run_suite

t = time.time()
viable, warnings = filter_viable_fixtures(list(GOLD_FIXTURES))
und = [w for w in warnings
       if isinstance(w, dict) and w['kind'] == 'baseline_undecidable']
strs = [w for w in warnings if isinstance(w, str)]
print('viable fixtures      :', len(viable), '/', len(GOLD_FIXTURES))
print('string warnings      :', strs)
print('undecidable warnings :', len(und))
for w in und:
    print('   ', w)

ids = {w['gold_id'] for w in und}
trials = run_suite(golds=viable, graders=[], undecidable_gold_ids=ids)
graded = [x for x in trials if not x.skipped_reason]
flagged = [x for x in graded if x.baseline_undecidable]
print('attempted trials     :', len(trials))
print('graded trials        :', len(graded))
print('graded + flagged     :', len(flagged))
print('elapsed %.1fs' % (time.time() - t))
PY
```

`graders=[]` is deliberate. Whether a trial is *skipped* depends only on
whether the mutation applied to that expression, not on any grader's verdict,
so the 196 / 118 counts are structural and need no grading pass. Running with
`[SymbolicGrader()]` would re-verify every mutated trial and take minutes
without changing a single number above.
